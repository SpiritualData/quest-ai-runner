# Evolvable structure (ESOI) in quest-ai-runner

This folder is the registry of how the repo is organised and the rules that keep it true. It applies the
evolvable-structure (ESOI) philosophy (structure that is stable where it should be and changeable where change is
expected) to QAR's architecture, not only to individual modules.

**To add or change something, start with [STANDARD.md](STANDARD.md).** It is the one shape every solution takes, with a
worked example, and it is enough to add a solution. The rules below are a reference: you meet them when
`python scripts/check_structure.py` names one, and each problem line starts with its rule id. `CLAUDE.md` is the
pre-flight checklist and `docs/ARCHITECTURE_STANDARDS.md` is the reasoning behind the code rules.

## Files

| File | What it holds | Edited by |
|---|---|---|
| `components.csv` | Placement only, one row per component: `component_id`, `layer`, `path` globs, `role`, `solutions` it serves | people and AI, by hand |
| `solutions.csv` | One row per solution: problem, ideal, port, implementations, `selected` and `selected_by`, `metric_kind` (`eval` or `invariant` with `invariant_reason`), metric and `metric_command`, `gap` and `action` | people and AI, by hand |
| `principles.csv` | The 13 principles of the evolvable-structure skill in short, and how each is measured here | people and AI, by hand |
| `waivers.csv` | Justified exceptions to a rule, each with a reason; each must still apply, so the list only shrinks | people and AI, by hand |
| `STANDARD.md` | The shape of one solution, a worked example, and how another repo adopts this | people and AI, by hand |
| `COMPONENTS.md` | A readable table of `components.csv` | generated by `--write-docs` |
| `tracker/*.csv` | The intent network as five Sheet tabs (problems, solutions, implementations, ideals, metrics), each with `tracking_*` columns, committed so the Sheet can be imported | generated by `scripts/build_tracker.py` (tracking columns are hand-edited and kept) |

Where things live: a place in the tree that owns a role is a component (`components.csv`); a problem with a port and
its implementations is a solution (`solutions.csv`); numbers live only in `evaluation/components/results.csv`.

## The rules

One list, in order. The check is `python scripts/check_structure.py` (no network, no model calls; `--strict` also
rejects runs recorded on uncommitted code, `--write-docs` regenerates the generated files). It also runs as
`tests/test_structure_registry.py`, so a normal test run fails when the structure drifts. Every rule has a mutation
case in `evaluation/components/check_the_structure/`.

1. **S1 coverage.** Every file belongs to exactly one component and every `path` glob matches a file (`*` stays in one folder, `**` crosses folders).
2. **S2 component rows.** Every row has a `role` and a `layer` from the known set.
3. **S3 root.** No `.py` file at the repo root.
4. **S4 size.** No module over 1,500 lines; split by role and re-export the old names (CLAUDE.md "Split rule"). Test files are waived.
5. **S5 docstring.** Every library module opens with a docstring that states its role.
6. **S6 direction.** Dependencies point inward: core < adapters < runner < config < cli/tools. A module imports its own layer or a lower one; `TYPE_CHECKING`-only imports are ignored.
7. **S7 solutions.** Every `Protocol` class is in the `port` cell of some solution; implementation paths and metric scripts exist; `selected` is a listed implementation or a selection-table name; no metric means a stated `gap` and `action`.
8. **S8 generated docs.** `COMPONENTS.md` matches `components.csv`.
9. **S9 waivers.** A waiver that no longer applies is deleted, and every waiver has a reason.
10. **S10 selection.** An `eval` solution's selected implementation is the leaderboard winner and has a recorded row, or a waiver names the pending decision and its owner; an `invariant` solution is never ranked.
11. **S11 metric kind.** Every solution is `eval` or `invariant` (an invariant states `invariant_reason`), and every solution is linked from some component's `solutions` (or waived), and every linked id exists.
12. **S12 measured code.** Every `evaluation/components/*/impls/*.py` drives live QAR code or declares itself an alternative (`ALTERNATIVE = True`, or a docstring opening `ALTERNATIVE`, `BASELINE`, `ABLATION` or `FLOOR`); a selected or measured implementation must be live, or waived.
13. **S13 config.** No `os.environ` / `os.getenv` in `core/`; core reads `CoreSettings`, which the config layer builds.
14. **S14 selection table.** Every solution with a port has an entry in `core/selection_table.py` and no entry lacks a row; a default is one of its implementations, and each implementation's module is listed in the row.
15. **S15 env docs.** Every environment variable read in `quest_ai_runner/` is a row of `docs/configuration.md` (generated from the code, described in `env_descriptions.csv`).
16. **S16 provenance.** The latest `results.csv` row of every implementation carries a `cases_sha`, or a waiver says why it cannot be re-recorded.
17. **S17 tracker.** The `tracker/*.csv` tabs match what the registry and `results.csv` now produce (only `tracking_*` columns are hand-edited).
18. **S18 ids.** Solution, component and tracker ids are unique, and no id repeats inside one cell.
19. **S19 serves.** Every component names at least one solution; code that serves none is removed, not waived.
20. **S20 complete.** Every solution has a problem, an ideal, implementations, a metric, a selected implementation and a recorded run on the current cases with a `git_sha`. Tests alone are not a metric.
21. **S21 evaluation folders.** Every `evaluation/components/<x>/` is named by some solution's `metric_command` or `metric`, or is listed shared; an orphan folder is deleted.
22. **S22 numbers.** No score, percentage, dollar amount or case count in a solution's `metric`, `gap` or `action` or in a waiver reason; numbers live in `results.csv`, read through the leaderboard.
23. **S23 selected is the table default.** For a solution with a selection-table entry, `selected` equals that entry's default.
24. **S24 recorded claims are true.** Every arm a `metric_command` names has a `results.csv` row, and a gap or action that says an implementation is "not recorded" (or says to "Record" it) names none that already has a row.

## Notes on the rules

* **Layers (S6).** A module's layer is its package, or for top-level modules the `layer` of its `components.csv` row
  (`config*`, `usage`, `pricing`, `resources` are config; `cli*`, `interactive_session*`, `textual_*` are cli). The
  runner takes the config layer's builders through `runner/config_wiring.py`, registered by the package `__init__`.
* **Eval and invariant (S10, S11).** Whether "best" can vary decides the kind; the reasoning, the leaderboard's
  "Invariant solutions" section and the `broken/` convention are in [STANDARD.md](STANDARD.md).
* **Selection table (S14, S23).** `resolve(solution_id, name)` picks the class (name, then
  `RunnerConfig.selections[solution_id]`, then the default). To switch one, set `[selections] "run-deep-work" = "acp"`
  in a lane's config file or edit the table default; to add one, add a table line and list its file in the row.
* **Results.** `evaluation/components/results.csv` is committed and records `git_sha`, `cases_sha` and `model` per
  run; the leaderboard compares rows only when `cases_sha` matches. Per-run JSON goes to `/tmp/qar_components/`.
  Private incident data is never committed.
* **Waivers.** Prefer fixing the cause. A waiver is a row in `waivers.csv` with a reason, and S9 removes it when it stops applying.
* **Principles.** `principles.csv` carries the P1 to P13 numbers of the evolvable-structure skill (renamed from
  adaptable-structure on 2026-10-15); the checks enforce them, so components do not claim them.
