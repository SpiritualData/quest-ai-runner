# Changelog

All notable changes to this project are documented here. The format is based on
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

- Everything new on a quest, written to a file in its folder (2026-11-20): `UpdateEngine.collect(consumer=...)` keeps one watermark per (quest, consumer, source), seeded from the old per-quest stamp; an autopilot run's advance is staged under its task id and committed by the executor only when the run is reported done (`UpdateEngine.settle`, `AutopilotPass.settle_run_context`), so a failed run keeps its news. New default sources `quest_collections` (the quest's linked and category collections found without a spec, plus the spec's `all_habits` and `include` with an entry `categories` filter; collections whose `lastEntryAt` is older than the watermark are never downloaded, created or edited entries count, every field is rendered by name) and `folder_files` (files added to the quest folder's `human_context/`, not `from_quest/`). `context_updates_file` writes one rolling `CONTEXT_UPDATES.md` per quest folder (newest section first, 30 days kept) and the prompt carries an index; `quest-ai-runner context-updates QUEST_ID [--folder] [--consumer] [--since] [--mark-seen] [--json]` runs the same engine. `QuestClient.list_collections` now follows every page. `quest_schedule.new_activity_since` counts the same sources for the reactive gate.

- An autopilot run for a quest with no folder in the lane's folder map starts by giving it one (2026-11-20): `quest-ai-runner quest-folder candidates|bind`, the safe `quest_folder_bind.bind_quest_folder` (one locked entry merged into `quest_folder_map_file`, refuses another quest's folder or a path outside `new_quest_folder_root`), a "FIRST STEP" section in the brief, and the poller re-reads the map file each scan so a new binding needs no restart. See docs/how-to/give-a-quest-a-folder.md.

- Every autopilot run's brief carries the ESOI skill's own text (2026-11-19, replacing the path line of the same day): a required section before the solution-improvement rule holds the `SKILL.md` of the evolvable-structure skill (or the skill `QAR_DEEP_WORK_SKILL` names), loaded from the ESOI library with `esoi.skill_text()` so it works on every install, with a lead line telling the run to apply it throughout, above all the core principle it asks you to remember; the frontmatter and generated-file notice are left out and the folder of its other files is named. An esoi without `skill_text` (0.7.0) is read from the same packaged file; if the library has no such skill, the old `QAR_SKILLS_ROOT` path line is used, else the section is left out with a logged warning. The section is about 8.3k estimated tokens of the 30k brief budget and is required, so optional context is cut first. `milestone_completion.skill_file` stays the one place a skill is located under a skills root.
- New client methods `convert_collection_to_habit(collection_id, **schedule)` and `convert_habit_to_collection(collection_id)` (2026-11-19) for `POST /api/data/collections/{id}/make-habit` and `/stop-habit`: turn one of the person's collections into a habit (schedule keys sent as given: habitType, frequency, days, time, times, startDate, questId, markExistingDone) and back, keeping every field and entry. Both return a `WriteResult` or raise `QuestWriteError` (a 409 when the collection is already in the target state).
- Collection entries can be read in chat (2026-11-19): the Quest retrieval adapter now answers two read-only operations, `list_collections` (the person's collections with their ids) and `list_collection_entries` (one page of a collection's entries, newest first, with the total count and the totals of its number fields; a page with more says so and is not totalled). The entries read takes the collection by the name the person uses (`args.collection`, matched exactly or by its words) or by `args.collection_id`, so one read reaches the rows; a name that matches none or several is answered with the collections and their ids. Both are listed by `list_operations` and described by `describe_operation`, and they are read as `query({operation, args})`. Before this, a read for a tracker's entries (e.g. an expense log) failed as an unknown query kind, the menu the planner was pointed to did not list it, and a spend question was answered as if nothing were recorded. A failed read is an error, never an empty collection.
- A usage limit that names one model no longer pauses the lane (2026-11-18): "your Fable limit resets Nov 21, 12pm" (or a session record's `seven_day_<model>` bucket) is read into `UsageLimit.model` and noted per model (`usage_limit.record_model`, persisted beside the lane-wide note), the model is skipped until its reset (`ModelRegistry` steps the tier to the nearest lower available tier, else the nearest higher, through `drop_unavailable`; a deep run switches to the next available model of its ladder, `fallback_ladder`), and the task goes straight back to the queue with no hold instead of waiting for the reset. Only a cap that names no model, or the case where no model is available, keeps the lane-wide hold. Before this, one model's limit held every task until its reset.
- New client method `create_autopilot(quest_id, fields)` (2026-11-17) for `POST /api/quests/{quest_id}/autopilots`: adds one named autopilot (the server mints its id); before it, a script could list, update and seed autopilots but not add one.
- Autopilot settings are seeded, never imposed (2026-11-16): `quest_ai_runner.body.internal_context.quest.autopilot_seed` (`seed_autopilot`, `seed_quest_autopilot`, `SeedLedger`) is the one way a script or pass writes autopilot settings it holds in files. A field (name, purpose, model, cadence, days, run time, mode, planning, instructions, rep, enabled, email recipients; at quest level instructions, timezone, environment) is written only when Quest has it unset or still holding what the seeding last wrote (hashes in a ledger file); any other difference is a reported conflict and Quest's value stays, unless `force` is passed. New client method `update_autopilot(quest_id, autopilot_id, fields)` for the per-autopilot PATCH. The runner's own poll passes never write autopilot settings (checked: the only caller of the quest-level write was by-hand scripts). Docs: `docs/how-to/named-autopilots.md`.
- Notes aimed at one autopilot (2026-11-16): a person's quest note may carry an `autopilot_id` (Quest backend; absent or null is quest-wide). An autopilot run's notes read (`quest_notes` spec key `autopilot_id`, set by the run) leaves out person notes aimed at another autopilot, puts the ones aimed at this autopilot first in the context updates block labelled as its instruction (`ContextUpdate.addressed`), and keeps such a note open until this autopilot's own run delivers a result after it. Assistant notes and quest-wide notes read as before; a reader that names no autopilot sees every note, as before.

## [0.7.7] - 2026-11-16

Release run: carries the Quest client's habit assignees, the undated backlog and a member's own Today, and the creation flow fixes (typed refused writes, strategy-map and habit methods, a habit needs no strategy). Esoi and hub pins unchanged (v0.7.0, v0.7.6).

- Quest client, habit assignees (2026-11-16): `assign_habit(habit_id, user_ids)` (an empty list means everyone), and `create_habit` and `update_habit` take `assigned_to_user_ids` (left out: the backend gives a new habit on a quest with 2 or more people to its creator; an empty list is everyone). A caller never needs a raw request for it.
- Quest client, Today and the undated backlog (2026-11-15): `move_goal_to_backlog` parks a goal with no date, `list_backlog_goals` lists what is parked, `schedule_goal_for_period` gives a goal a period (how one leaves the backlog), `abandon_goal` drops one, and `show_habit_on_my_today` takes a shared habit off the caller's own Today or puts it back. These need a Quest backend that carries the same routes.
- Quest client, creation flow fixes (2026-11-15): a refused specification or intent write (`create_spec_record`, `edit_spec_record`, `archive_spec_record`, `reorder_solutions`, `refresh_spec`, the intent writes) is now a typed `WriteResult` with status refused, failed or unknown, falsy, still readable like the refusal body (`result.get("refused")`, `result["code"]`); before it was a plain dict, so `quest-ai-runner quest` printed it and exited 0. New methods: `get_strategy_map`, `set_solution_answer`, `set_solution_picks`, `set_solution_reviewed`, `create_map_strategy`, `update_map_strategy`, `delete_map_strategy`, `update_habit`, `resume_habit`, `disable_habit`. `create_habit` takes `None` for the strategy (a quest with no strategies still takes a habit), and the `create_quest_habit` tool no longer refuses such a quest. Docs follow Quest: a quest's autopilot setting never refuses a specification write, an experiment's `phase` words are the one vocabulary (`status` takes them too), and its long procedure goes in `protocol`. These need a Quest backend that carries the same changes.

## [0.7.6] - 2026-11-15

Release run: carries everything since 0.7.5 (named autopilots, the model call budget and volume guards, the Quest client's org and team member methods, `request_autopilot_run`, `update_rep`, children run without API-billing credentials, ESOI planner record). The hub pin moves to v0.7.6, which exports `CallGuard`, `CallLimits` and `CallBudgetExceeded`.

- Named autopilots, review fixes (2026-11-15): a scheduled run that waited past its grace is skipped "missed: the lane was down"; the email contract reads the autopilot's own `email.enabled` from the autopilots list; on duty is the backend's `status.runs_today` (the weekly days rule only when absent); the last-run block is the autopilot's own `autopilot_run` rows; `skipped` counts as a task status; the routing day is UTC without a zone; the old pass retirement runs until a scan finds none open and then stops; lanes without an update engine read captures since the autopilot's own previous run.
- Named autopilots (2026-11-15): a quest holds any number of named autopilots and the backend schedules them, one `autopilot_run` task per run (its `autopilot_id` is a task field, never read from text). The runner executes the run inside that one task: it skips with a reason when the autopilot does not run (paused, past the plan's cap, removed), holds automatic extra runs to 3 per autopilot a day and the team budget (never a scheduled run or Run now), applies backpressure per autopilot, asks a registered work source (`learning`) what is due, routes the quest's eligible goals by scope with one fast-tier judgment per quest per day (`autopilot_routing`: a goal belongs to one on-duty autopilot or to none, a rep's goal stays with that rep), composes one brief and then parks it as `suggested` (suggest) or runs the deep agent on it (act); a run with nothing to work is closed as skipped ("no goals relevant to this scope"). At most one autopilot run per quest folder is in flight, quests taken in turn. Removed: the per-quest pass series and everything that scheduled it (`_create_quest_pass` and its retune, catch-up and run-request code, now retire-only), `RoutinePass` and `poller_routines`, the roster day rule and persona routing (`resolve_persona`, `personas_on_duty`), quest-level bookkeeping (`last_pass_at`, `routine_runs`, `autopilot_state`), the goal-proposal path and the autopilot work task. `GatePurpose` is now `WorkSource` (`autopilot_sources.py`). The hub's Proactivity gains `next_due` and a `recurrence` schedule (daily to yearly, nth weekday or day of month). How-to: `docs/how-to/named-autopilots.md` (replaces `single-purpose-autopilots.md`). ESOI: metric `metric-quest-autopilot-goal-routing` (`route_goals_to_autopilots`, model-free first) and the run gate cases of `gate_an_autopilot_pass` rewritten for runs.

- Model call budget and volume guards (2026-11-15, after a night of unattended calls): `QAR_MAX_LLM_CALLS_PER_JOB` (200) and `QAR_MAX_LLM_CALLS_PER_HOUR` (600) raise `LlmBudgetExceeded`, named jobs (`llm_job`) step requests above balanced down to balanced after 20 calls, the best tier runs only for a person's explicit request (`QAR_BEST_REQUIRES_USER_REQUEST`), and the context index skips every model stage over 3000 files or cards and caps each run at 300 new files and 100 stale cards.
- Call guard is the hub's (2026-11-15): `spend/llm_budget.py` is now a thin adapter that reads `QAR_MAX_LLM_CALLS_PER_JOB`, `QAR_MAX_LLM_CALLS_PER_HOUR`, `QAR_BEST_REQUIRES_USER_REQUEST` and the new `QAR_KEYLESS` (1: no API key is ever used) and `QAR_NEVER_MODELS` (comma list) into one `CallLimits` and one process-wide `CallGuard`, handed to the hub's `MultiProvider` as `call_guard=`; the counting, step-down and best rules, and `BudgetedMultiProvider`, are gone from QAR (errors are the hub's `CallBudgetExceeded`, `ModelNotAllowed`, `KeyedCallRefused`). The structure watch asks for `best` again and runs inside `guard.role("structure-watch")`. Needs the next hub tag (the `pyproject.toml` pin is not moved yet).

## [0.7.5] - 2026-11-15

- Release run (2026-11-15): the five container folders and modules lose their leading "the" (`body`, `consciousness`, `intelligence`, `world`, `self`), following the hub's 0.7.5; consumers import `quest_ai_runner.intelligence...`, `quest_ai_runner.world...` and so on from this tag, and 0.7.4 and earlier use the old paths. The hub pin moves to `v0.7.5`. Also: the planner default row is realigned (an extra empty cell shifted every column, so a chat turn failed with an unchosen-default error); autopilot acts on answered asks and closes out what it acted on; a tool name the planner made up is refused with the next step; slim task reads for cancel and pause checks and slim progress replies; opencode screen fixes (a note typed mid-run reaches the next attempt, a not-met goal says why, resume shows the earlier turns).

Older versions (0.7.4 and earlier): see CHANGELOG_archive.md
